# Phase 20: AI / LLM Security Testing Framework

## Overview
The AI / LLM Security Testing Framework introduces a comprehensive, authorized testing capability designed specifically for AI applications, agents, and Large Language Models. It enables researchers to safely probe AI boundaries, prompt injection vectors, and RAG constraints without risking production system stability or executing uncontrolled commands on the host.

## Architecture & Trust Boundaries

The system relies on strict trust boundaries across the LLM and the execution environment:
- **SYSTEM**: Immutable application instructions.
- **DEVELOPER**: Framework configuration.
- **USER**: Untrusted input originating from the security researcher's test cases.
- **RETRIEVED DATA**: Untrusted external documents (e.g., RAG sources).
- **TOOL OUTPUT**: Execution outputs.

The framework is configured to flag any instance where lower-tier trust inputs (like `USER` or `RETRIEVED DATA`) successfully override `SYSTEM` instructions.

## Key Components

### 1. AI Application & Endpoint Inventory
- `AIApplication`: Represents a target AI service (e.g., a local RAG chat app).
- `AIEndpoint`: Specific entry points (e.g., `POST /api/chat`, `POST /api/agent`).

### 2. AI Test Cases
Test cases map to specific endpoint behaviors. The framework supports categories such as:
- **PROMPT_INJECTION**: Direct instruction override.
- **INDIRECT_PROMPT_INJECTION**: Poisoned data loaded via external sources.
- **RAG_POISONING**: Documents attempting to assert authority over the system prompt.
- **SENSITIVE_INFORMATION_DISCLOSURE**: Leaking API keys or secrets.
- **SYSTEM_PROMPT_LEAKAGE**: Extracting internal system instructions.
- **INSECURE_OUTPUT_HANDLING**: The AI returning unescaped HTML/JS.
- **TOOL_ABUSE & EXCESSIVE_AGENCY**: The AI invoking internal functions outside its authorized scope.

### 3. Local AI Security Lab
A deliberately vulnerable fixture is provided at `http://127.0.0.1:9100`. It includes endpoints (`/api/chat`, `/api/rag`, `/api/tool`, `/api/agent`) that simulate prompt injection, RAG poisoning, tool authorization failures, and system prompt leakage using entirely synthetic data (e.g., `AI_BUGHUNTER_TEST_SECRET_7F3A`).

**CRITICAL RULE:** No real secrets (AWS keys, real OpenAI keys, etc.) should ever be placed in the Local AI Lab.

### 4. Test Lifecycle & Safe Executor
AI Test Cases (`AITestCase`) are converted into `TestPlan` records.
- They are subject to the same `SafeExecutor`, `Kill Switch`, and `ScopeValidator` controls as standard web application tests.
- Execution requires explicit Human Approval. The framework will **never** automatically execute a test case against an unapproved target.

### 5. Semantic Validation & AI Security Analyzer
The `AISecurityAnalyzer` evaluates the request, response, and program policy.
- It determines if a vulnerability was successfully exploited (e.g., did the AI actually leak the secret?).
- It returns structured JSON using a strict schema.
- **Semantic Validation**: The AI is strictly forbidden from outputting `VALIDATED` or `RESEARCHER_CONFIRMED`. All findings default to `NEEDS_VALIDATION` and must be manually reviewed.

## Finding Validation
Findings generated by the AI Security framework follow the exact same lifecycle as web vulnerabilities. They appear in the Finding Validation Queue and require manual triage.

## Security Guarantees Confirmed
1. **Scope Protection**: The AI cannot scan or attack endpoints not explicitly allowlisted.
2. **Approval Gate**: AI tests remain in `PLANNED` state until a human approves them.
3. **No Automatic Exploitation**: The AI Advisor cannot issue commands to attack the lab directly.
4. **Data Isolation**: Program A's AI test cases and findings are completely isolated from Program B.
